Three.js 如何解析 URDF 机器人模型

机器人可视化的第一步，是把一个 URDF 文件变成 Three.js 场景里能渲染、能动的东西。

这件事听起来像是「加载一个模型」，但 URDF 根本不是模型文件。它里面没有顶点、没有法线、没有材质贴图，只有一个 XML 骨架，描述机器人由哪些刚体组成、这些刚体怎么连起来。真正的几何体（STL、DAE）是另外的文件。

所以 Three.js 要做的，是把这套「关系描述」翻译成一棵 Object3D 树。这篇分两部分：先讲 URDF 到底描述了什么，再逐段拆 URDFLoader 的源码，看它每一步在干什么。

1. 什么是 URDF

URDF 全称 Unified Robot Description Format，是 ROS 里的机器人描述格式，本质就是一个 XML。

它只回答两个问题：

  • 机器人身上有哪些刚体 —— 用 <link> 描述
  • 这些刚体怎么连、怎么动 —— 用 <joint> 描述

注意图里右边那张桌子，旁边也标了一句 “also a link”。这是很多人第一次看这张图会卡住的地方：link 不一定是机器人身上的零件。桌子、地面、相机支架，只要它参与坐标变换，就可以是一个 link。

2. link：一个刚体的三重描述

先从最小的单元看起：

link 标签中的 name 表示该连杆的名称，我们可以自定义。未来 joint 连接 link 的时候，会使用到这个名称。

<visual>：看上去是什么样

<visual> 描述机器人的外观：

  • <geometry> 表示几何形状。这里用 <mesh> 调用了一个在三维软件中提前设计好的蓝色外观，也就是那个 stl 文件，看上去和真实机器人是一致的。
  • <origin> 表示坐标系相对初始位置的偏移，分别是 x、y、z 方向上的平移，和 roll、pitch、yaw 旋转。不需要偏移的话，就全为 0。

<collision>：碰撞时算成什么

第二个部分 <collision> 描述碰撞参数。里边的内容似乎和 <visual> 一样，也有 <geometry> 和 <origin>，看似相同，其实区别还是比较大的：

  • <visual> 重在描述机器人看上去的状态，也就是视觉效果；
  • <collision> 则是描述机器人运动过程中的状态，比如机器人与外界如何接触算作碰撞。

在这个机器人模型中，蓝色部分是通过 <visual> 来描述的。在实际控制过程中，这样复杂的外观在计算碰撞检测时要求的算力较高；为了简化计算，我们把碰撞检测用的模型简化为了绿色框的圆柱体，也就是 <collision> 里边 <geometry> 描述的形状。

<origin> 坐标系偏移也是类似 —— 它可以描述刚体质心的偏移。视觉模型的几何原点未必在零件的旋转中心上，但碰撞体通常要摆在质心附近，两个 <origin> 就此分道扬镳。

<link> 里其实还有第三块，上面那段示例没写，但真实文件里都有：

3. joint：把 link 连成一棵树

机器人模型中的刚体最终要通过关节 joint 连接之后，才能产生相对运动。

URDF 中的关节有六种运动类型：

关节类型 描述
continuous 旋转关节，可以围绕单轴无限旋转
revolute 旋转关节，类似于 continuous，但是有旋转的角度极限
prismatic 滑动关节，沿某一轴线移动的关节，带有位置极限
fixed 固定关节，不允许运动的特殊关节
floating 浮动关节，允许进行平移、旋转运动
planar 平面关节，允许在平面正交方向上平移或者旋转

对应到实际零件：

  1. continuous 描述旋转运动，可以围绕某一个轴无限旋转，比如小车的轮子，就属于这种类型。
  2. revolute 也是旋转关节，和 continuous 类型的区别在于不能无限旋转，而是带有角度限制，比如机械臂的两个连杆，就属于这种运动。
  3. prismatic 是滑动关节，可以沿某一个轴平移，也带有位置的极限，一般直线电机就是这种运动方式。
  4. fixed 固定关节，是唯一一种不允许运动的关节。不过使用还是比较频繁的，比如相机这个连杆，安装在机器人上相对位置不会变化，此时使用的连接方式就是 fixed。
  5. floating 是浮动关节，第六种 planar 是平面关节，这两种使用相对较少。

4. Three.js 解析 URDF

整个流程的入口是 load()：取到 URDF 文本、交给 processUrdf 解析、再把结果回调出去。这里面有两行容易被看漏的 itemStart / itemEnd。

这里没有用 FileLoader，而是直接 fetch + res.text() —— 因为 URDF 是 XML 文本，不需要任何额外的解析钩子。

值得注意的是手写的那对 manager.itemStart(urdfPath) / manager.itemEnd(urdfPath)。

LoadingManager 内部维护一个「还有几件事没做完」的计数器，平时是 FileLoader 自己调 itemStart / itemEnd。但这里用的是原生 fetch，LoadingManager 完全不知情。如果不手动补上这两句，会出现一个很隐蔽的问题：URDF 主文件还没下载完，manager.onLoad 就已经触发了（因为此刻计数器是 0），外部拿到一个还没建好的机器人。

补上之后，URDF 主文件和它引出的所有 STL/贴图，全都算在同一个计数器里，「全部加载完成」这个信号才准。这一点在 4.4 节讲 <mesh> 异步加载时会再回来看。

4.1 把 XML 变成 DOM

这里没有引入任何 XML 库，直接用浏览器原生的 DOMParser，MIME 类型指定 application/xml。

这是整个解析流程里最省事的一个决定。 一旦拿到 Document，后面所有的查找、遍历、取属性，都可以用现成的 DOM API —— querySelector、getAttribute、children。手写正则或者用 fast-xml-parser 反而要把这些重新发明一遍。

方法签名允许 string | Document | Element 三种输入，是为了让外部可以传入已经解析好的 DOM，避免重复解析。

filter(...).pop() 这一串是防御性写法：parseFromString 在某些浏览器上会在文档前插入节点，取最后一个匹配到的 robot 更稳；解析失败时返回的是一份带 parsererror 的文档，这里则返回 undefined，让调用方拿到 null 而不是崩溃。

4.3 解析材质

三类里最先处理的是 <material>：

对应的是这样的 XML：

processMaterial 是这一节的核心 —— 它把一个 <material> 元素翻译成一个 Three.js 材质对象：

整个函数就一句话可以概括：先取一个默认材质，再拿 XML 里的字段往上覆盖。 但和 Three.js 结合的这四个点，每一个都有讲究。

一、基底是 createCommonMaterial()，不是 new Material()。

第一行先取一份默认材质，再往里填东西。这个默认材质是个三参数的 MeshStandardMaterial（color: 0xcccccc、metalness: 1、roughness: 0.1）。

这意味着即使 <material> 里只写了一个 <color>，最终出来的也是一个 PBR 材质，而不是 MeshBasicMaterial 那种纯色 —— URDF 只描述「什么颜色」，而 Three.js 拿到的是一套完整的 PBR 参数。

二、opacity 和 transparent 必须成对出现。

在 Three.js 里单独设 opacity 是不生效的。 只有 transparent = true 时，材质才会进入透明渲染队列、开启混合。设了 opacity = 0.5 但 transparent = false，渲染出来还是完全不透明 —— 这是 Three.js 里最常见的「为什么我的透明没效果」之一。

那为什么不干脆无条件 transparent = true？因为透明物体要参与排序、通常还要处理深度写入，是有实打实开销的。用 rgba[3] < 1 判一下，只有真正需要透明的材质才付这个代价。

三、setRGB 传了三个参数，没做色彩空间转换。

Color.setRGB(r, g, b) 的第四个参数是 colorSpace，缺省时按 working color space（线性空间） 解释 —— 也就是不做任何转换。

而 URDF 里写的 rgba 值，惯例上是给人看的显示值（sRGB）。上面 h1_2.urdf 里的 rgba="0.1 0.1 0.1 1"，按线性解释出来会明显比「看起来的 0.1」要亮。如果发现模型颜色比预期发灰发亮，这里是第一个该看的地方。

四、贴图那一支更微妙。

拆成三个点：

  • loader.load() 是同步返回一个空的 Texture 对象的，图片之后才异步填进去。所以这一行不会阻塞，material.map 立刻就有值，只是此刻 image 还是空的 —— Three.js 会在图片 onload 之后自动上传 GPU 并把 needsUpdate 置为 true。模型先白几帧、贴图再「跳」出来，就是这个机制。
  • TextureLoader 传了 manager，所以贴图也在加载计数器里，manager.onLoad 会等它 —— 和 4.4 里 STL 的处理是同一个道理。
  • colorSpace = SRGBColorSpace 必须显式设。 Three.js 对贴图的默认假设是 NoColorSpace，也就是「这是线性数据，直接用」。但 JPG/PNG 里存的像素值是 sRGB 编码的，少了这一句，未解码的数值会直接进光照计算，结果就是整体偏亮、对比度发灰。

注意三和四是两个相反的方向：setRGB 是把值当作线性用（不转换），texture.colorSpace 是声明「这来自 sRGB」（shader 里会解码）。同一个函数里两条路径的处理并不一致 —— URDF 的颜色语义本身没有严格规定，两边只能各自约定。

最后，material.name = materialNode.getAttribute('name') 把 URDF 里的名字带到了 Three.js 对象上。这不只是好看 —— 调试时能在 scene 树里一眼认出哪个材质是哪个，也方便后续按名字批量替换。

子标签 一个 link 里能有几个 挂上去的是什么
<visual> 任意多个 每个一个 LinkVisual

<collision> 那行是唯一一个「多个 XML 节点合成一个 Three.js 对象」的写法 —— 对比 <visual> 是来一个建一个。这个不对称是刻意的：运行时往往要整体开关碰撞体显示、整体换色，合成一个 Group 比一堆散落的 Mesh 好用得多。

还有一点：这三个分支挂上去的东西都挂在 urdfLink 这一层，共享同一个坐标系。它们各自的 <origin> 只是把自己再挪一下。所以「视觉模型在原位、碰撞体偏到质心」这类差异，靠的是各自的 <origin>，而不是挂到不同的父节点上。

几个容易忽略的点：

球：URDF 只给 radius，Three.js 还必须给宽高段数。这里写死 8, 6，是相当低的多边形数 —— 因为 <sphere> 在这类模型里几乎只出现在碰撞体上，本来就不需要圆。

圆柱：径向段数同样只有 6，也就是个六棱柱。同样出于「简化碰撞检测算力」的考虑 —— 和 2. 节里说的「把复杂外观简化成圆柱体」是同一个动机的延伸。

几个点：

一、STL 和 DAE 的产物类型不一样。 STLLoader 只吐 BufferGeometry，所以这里得自己 new Mesh；ColladaLoader 吐的是完整的 dae.scene，一个 Group，还可能带层级，所以那边是 traverse 进去逐个 Mesh 换材质。下游代码不能假设 obj instanceof Mesh —— 这也是 parent.add(obj) 的形参类型是 Object3D 而不是 Mesh 的原因。

二、scale 用 multiply 而不是 set。 DAE 文件自带缩放（Collada 常以厘米为单位），set 会把它覆盖掉，multiply 才是叠加。

三、parent.add(obj) 发生在 Promise 里。

这就是时序问题的根源：processUrdf 从头跑到尾、把 urdfRobot 返回出去的时候，所有 mesh 都还没回来。外部 onLoad 回调拿到的是一个「骨架已经搭好、但身上还光着」的机器人。

回到第 4 节的引子 —— 现在能说清那对 itemStart / itemEnd 的真正价值了。上面每个 new STLLoader(manager) 都传了同一个 manager，所以每个 STL 的加载都会自动进出计数器；而 URDF 主文件由 load() 手动 itemStart。两件事加在一起，manager.onLoad 才真正代表「URDF 和它引出的所有网格都齐了」。

四、路径解析交给了 resolveSubPath。

默认原样返回。这个钩子存在的原因是：URDF 里的 filename 经常是 package://my_robot/meshes/arm.stl 这种 ROS 包路径，浏览器根本不认识；也经常是相对 URDF 文件自身的路径 ./models/h1_2_description/meshes/pelvis.STL，而 URDF 和网页并不在同一个目录下。

同一个文件在 ROS 里能被 rviz 正确加载、在浏览器里却 404，绝大多数情况都出在这里。把它做成可重写的方法，而不是写死一段路径拼接逻辑，就是让每个项目自己决定映射规则。

函数签名把参数写成 urdfLink: Group 而不是 URDFLink，因为 processLink 只把它当容器用，不关心具体是哪个子类。同理，4.7 里 <visual> 和 <collision> 共用的那个 processOriginAndGeometry，它的 parent 参数也是 Group —— 既能接 LinkVisual，也能接碰撞体的容器。

URDFLink 只是个 Group，没有额外能力：

整个加载器里最漂亮的一行是那个 querySelector。

树的根是「没人把它当孩子」的那个 link。与其建完整棵树再回溯找根，不如换个角度问：这个 link 有没有在某个 <joint><child link="..."> 里出现过？ 一次 querySelector 全库扫描就能回答，不需要递归、不需要拓扑排序。

代价是复杂度 O(n²)：每个 link 扫一遍全文档。但机器人撑死也就几十上百个 link，这个量级下完全无所谓。

值得一提的是，<joint><parent link="..."> 里也有 link 属性，但选择器写的是 child[link=...]，只匹配标签名是 child 的元素，所以不会被父节点干扰。

顺序上也有讲究：这里只把根 link 挂到了 urdfRobot 上，其余 link 此刻都是「孤岛」，还没进树 —— 它们要等 4.6 把 joint 挂成树时才被认领。

4.5 解析 joint

<joint> 是 URDF 里信息量最大的标签。逐段看 processJoint。

第一步：判断它是不是从动关节。

带 <mimic> 的创建 URDFMimicJoint，其余创建 URDFJoint。两个属性缺省时分别按 1 和 0 处理 —— 这是两个有意义的默认值：不写 multiplier 表示 1:1 跟随，不写 offset 表示零点对齐。它们描述的关系就是 从动角度 = 主动角度 × multiplier + offset，人手的三段手指、机械夹爪的两个爪片都是这个结构。

第二步：给关节挂上坐标系辅助对象。

每个 joint 一个，用来把关节自身的坐标系画成三根彩色轴，长度 0.2，默认隐藏。

注意它的创建时机 —— 在遍历子标签之前。因为 jointObj.add(jointAxisHelper) 是把它挂成 joint 的子节点，后面无论 joint 被挂到哪个 link 下、怎么变换，这个辅助对象都自动跟随。这也是 4.6 要建立的树结构第一次发挥作用。

第三步：遍历子标签，分五路归档。

五个分支各自归档了什么：

子标签 写到哪儿 用途
<origin> position / quaternion + userData.origPosition / origQuaternion 关节相对父杆的位姿，存两份
<parent> 树结构 见 4.6
<child> 树结构 见 4.6
<axis> userData.axis 关节的运动方向轴
<limit> userData.limit.lower / .upper 角度或位移范围

五个分支里，<origin> 和 <axis> 是重点 —— 它们是关节能「动」的全部依据，也是整个解析里和 Three.js 绑得最紧的两处。

一、<origin>：同一个位姿为什么要存两份。

同一个位姿写了两遍：一遍写进 Three.js 真正拿去渲染的 position / quaternion，一遍存进 userData 的 origPosition / origQuaternion。

为什么要留底稿？ 因为关节动起来之后，位姿会被反复改写。驱动关节时，每次都从初始姿态重算新姿态，而不是在上一帧的基础上继续叠加：

没有 origPosition / origQuaternion 这两个锚点，关节就只能做增量更新 —— 那样既会累积浮点误差，也没法从任意角度跳回任意角度。后面的时间轴回放，靠的正是这一点。

还要注意这四行的顺序：先 position.set，再 applyEulerZYX，最后才 copy 出 origQuaternion。抄底稿必须在旋转算完之后 —— 抄早了，存下来的就是旋转前的单位四元数，底稿等于没存。

applyEulerZYX 里那个 'ZYX' 是本节最大的坑，4.7 单独讲透。

二、<axis>：存的是「关节坐标系里的方向」。

这里只是把三个数存进 userData.axis，没做任何坐标变换。这不是偷懒，而是对的 —— URDF 规定 <axis> 表达在 joint 自己的坐标系里，而 joint 的坐标系正是 position / quaternion 所定义的那个。Three.js 后续用到这个轴时，会自己把它带进当前坐标系：

  • 旋转关节：setFromAxisAngle(axis, n) 直接用。因为构造出来的四元数本来就作用在 joint 的局部坐标系上，不需要额外转换。
  • 滑动关节：_tempAxis.copy(axis).applyQuaternion(this.quaternion) —— 得先用当前姿态把轴转到父坐标系，才能拿去做 position 的平移。

如果把 <axis> 当成世界坐标或父 link 坐标来处理，方向就全错了。 这是 URDF 里仅次于 rpy 顺序的第二个方向陷阱 —— 而且比 rpy 更隐蔽，因为轴错了往往只表现为「关节在绕一个奇怪的方向转」，不容易一眼看出是解析阶段的问题。

还有一个细节：<axis> 在 URDF 里是可选的。省略时按 (1, 0, 0) 处理 —— 这个默认值写在 URDFJoint 的 userData 初值里（axis: new Vector3(1, 0, 0)），所以这个分支不执行时，axis 也依然有值。

三、<limit> 只取 lower 和 upper。 标签上还有 effort（力矩上限）和 velocity（速度上限），但那是给动力学和轨迹规划用的，渲染用不上，直接忽略。而且这里是「有才赋值」的写法 —— lower && (limit.lower = ...)，属性缺失时保留 userData 里的默认值 { lower: 0, upper: 0 }。

四、userData.type 最后才写。 遍历子标签时用不到类型，而驱动关节时要用，所以在对象完全建好之后一次性写入。

关节的位姿从这里来：

四行，每一行都在和 Three.js 的数学类型打交道。 逐行拆开：

行 做什么 涉及的类型
tempEuler.set(r, p, y, 'ZYX') 用 URDF 的 rpy 填一个欧拉角，并指定旋转顺序 Euler
tempQuaternion.setFromEuler(tempEuler) 把欧拉角转成四元数 Euler → Quaternion
tempQuaternion.multiply(obj.quaternion) 叠加上 obj 原有的旋转 Quaternion × Quaternion
obj.quaternion.copy(tempQuaternion) 写回对象 Quaternion

为什么中间要绕一下四元数，不直接把 rpy 赋给 obj.rotation？

因为 obj.rotation 是个 Euler，它自己也有一个 order 属性，默认就是 'XYZ'。如果图省事写成：

顺序照样是错的 —— 坑并没有绕着走，只是换了个地方。

所以要么额外记得设 obj.rotation.order = 'ZYX'，要么就像这里一样：用临时 Euler 指定顺序、转成四元数再写回。后者的好处是只写四元数、不碰 rotation 的 order。

这背后是 Three.js 里的一个设定：Object3D 的 rotation 和 quaternion 是同一个旋转的两个视图，内部靠回调互相同步 —— 写 quaternion 会自动按 rotation 当前的 order 重新解算出对应的欧拉角。所以无论走哪条路，最终存下来的旋转是同一个；差别只在于「用哪个 order 去解释那三个数」。

tempEuler 和 tempQuaternion 是模块级的临时对象。

定义在 utils.ts 顶部，而不是在函数里 new。这是 Three.js 代码里极常见的写法：几何变换在一帧里会被调用成百上千次，每次 new 两个对象就是上千次堆分配、上千次 GC 压力。复用两个模块级实例，代价是函数不可重入 —— 但在单线程的渲染循环里这不是问题。

5. URDF坐标系转成threejs坐标系

URDF 用的是 ROS 的坐标系：z 轴朝上（x 向前、y 向左、z 向上）。Three.js 默认 y 轴朝上。两者差一次旋转，转换在场景层完成：

把所有机器人和路径挂进一个 tfGroup，给 tfGroup 绕 x 轴转 -90°，再把 tfGroup 加进场景。整棵子树的局部 z 轴于是对齐世界的 y 轴。

URDFLoader 不做这件事 —— processUrdf 里没有任何一处改坐标轴，URDF 里 xyz 写多少就解析成多少。
