python异步编程

asyncio 是 Python 3.4 版本引入的标准库，用于编写单线程并发代码，主要处理网络 I/O、文件 I/O 等。它使用 async / await 语法，让异步代码看起来像同步代码一样直观。

Python 异步编程主要就是：当一个任务正在等待网络、数据库、文件或定时器时，不让程序傻等，而是先去执行其他任务。 它解决的核心问题是：大量任务都要等待时，怎么更高效地利用这段等待时间。

这就是 asyncio 的全部价值所在。它没有让单个请求变快，它让等待的时间被重叠起来。

2. 四个概念

概念 是什么
协程 Coroutine 用 async def 定义的异步函数。调用它不会立即执行，而是返回一个协程对象
事件循环 Event Loop 异步编程的核心，负责调度协程，在 I/O 等待时切换任务
Future 代表一个异步操作的最终结果，可以把它当作一个”未来完成”的容器
Task 是 Future 的子类，用于在事件循环中调度协程

还有一个容易被忽略的前提：asyncio 通常也运行在主线程上。 它不创建线程，只是在同一个线程里，趁某个协程在等 I/O 的时候切去跑另一个协程。

await 写在协程里面，含义是”在这里等这个操作完成，等的时候把执行权让出去“。这句话的后半截是关键——await 不只是”等”，它是”等，但不占着位置等”。

一个容易漏掉的规则：await 只能写在 async def 里面。 普通函数里写 await 直接语法错误。

5. create_task 之后，为什么不用立刻 await

很多人第一次看这段代码会觉得奇怪：

任务明明没被 await，怎么就跑了？

因为 create_task() 会把任务添加到事件循环中进行调度，事件循环会自动运行这些任务，不需要显式 await。

具体发生了三件事：

  1. 任务被调度 —— 任务被添加到事件循环（event loop）中排队
  2. 立即执行 —— 任务会在事件循环的下一个周期开始执行
  3. 并发运行 —— 任务与当前代码以及其他任务并发运行

那 await 是干什么的？它的作用是：

  1. 等待任务完成 —— 暂停当前协程，直到任务完成
  2. 获取结果 —— 拿到任务的返回值
  3. 异常处理 —— 传播任务中发生的异常

但 await 不是触发任务执行的必要条件。

所以在最外层，await task 和 create_task 是两件事： 前者是”要不要现在等结果”，后者是”有没有把这个协程排进调度”。当然，如果你创建了 Task 却从头到尾不 await，任务里抛的异常就没人接，Python 会打一条 Task exception was never retrieved 的警告——不 await 可以，但要保证异常有别的出口。

gather 那一节其实就属于”别的出口”：它一次接管了所有任务的等待和异常传播。

6. 取消和超时

task.cancel()

三点要注意：

  • cancel() 是”请求取消”，不是”立刻停”。 它给协程抛一个 CancelledError，但只有在这个协程跑到下一个 await 时才会真正抛出。所以上面 await asyncio.sleep(1) 那个点才是取消生效的地方。
  • CancelledError 继承的是 BaseException，不是 Exception。 所以 except Exception 抓不到它——这是故意的，免得你顺手把取消给吞了。
  • 协程内部抓到 CancelledError 之后应该 raise 出去。 上面那个 raise 就是这个意思：打印完日志要继续往外抛，让 await task 那边也收到。吞掉不抛，上层会以为任务正常结束了，但实际上是半途停下的。

还有一点容易漏：取消之后最好 await 一下这个 task。 上面把它放在 try 里 await，是为了让取消有时间真正落地，不然警告和状态都不确定。

asyncio.wait_for

asyncio.wait_for() 的意思是：等一个异步操作，但最多只等指定时间。

这里就是：等 task 完成，但最多等 3 秒。3 秒内完成就返回结果；超过 3 秒还没完成，就抛 asyncio.TimeoutError。

有一处可以简化：wait_for 超时的时候，它自己已经把传进去的那个任务取消掉了（文档原话是 “If a timeout occurs, it cancels the task and raises TimeoutError”）。所以上面 except 里那句 task.cancel() 是多余的，留着无害，但知道它多余能省掉一次误判——排查”任务被取消了”这类问题时，记得 wait_for 本身就是嫌疑人之一。

两个版本上的细节：

  • Python 3.11 起，asyncio.TimeoutError 就是内置的 TimeoutError（asyncio.TimeoutError is TimeoutError 为 True）。所以老代码里写 except asyncio.TimeoutError，新代码直接写 except TimeoutError 就行，现在只是留个向后兼容的别名。

三种取法

写法 队列为空时
await queue.get() 一直异步等，直到有数据

用一句话记：

  • await asyncio.wait_for(queue.get(), 0.5) → 没消息最多等 0.5 秒
  • queue.get_nowait() → 不等，有就拿，没有就直接报错

wait_for 那一档的用处是”别永远卡在 Queue 上“：等待期间可以醒过来，检查一下别的状态（比如生产者是不是已经结束了）。

11. 线程、进程、协程

最后把这三个放在一起。

进程 线程 协程
调度者 操作系统 操作系统 事件循环（程序自己）
资源 独立内存空间，互相隔离 共享进程内存 共享所在线程的内存
切换时机 随时，由 OS 决定 随时，由 OS 决定 只在 await 处主动让出
开销 最大 中等，每个线程一条独立栈 最小，一个线程能跑大量协程
能并行吗 能，多核并行 受 GIL 限制，纯 Python 字节码不能同时跑；I/O 可以并发 单线程并发，不是并行
阻塞的影响 只卡自己 只卡自己 卡住整个事件循环
适合 CPU 密集 同步阻塞 I/O、老的同步 SDK 大量异步 I/O

几点展开：

调度者不同。 线程是操作系统调度的执行单元，创建之后由操作系统决定什么时候运行、暂停和切换；协程是用户态的轻量级执行单元，由程序主动调度，执行到 await 才暂停让出。线程切换是被动的，协程切换是主动的。

切换方式不同。 线程可能在任意时刻被 OS 切走；协程只在 await 处切。这带来一个直接后果：协程之间的代码在两次 await 之间是不被打断的，所以共享数据通常不用加锁——这也是为什么 asyncio 里很少见到 Lock。

GIL 那一栏要说清。 在普通 CPython 中，由于 GIL，多个线程通常不能同时执行纯 Python 字节码；但 I/O 操作会释放 GIL，所以 I/O 并发是有效的。这正好解释了为什么线程和协程都适合 I/O、都不适合 CPU 密集。

阻塞影响不同。 一个线程执行阻塞操作，通常只阻塞该线程。但协程里执行同步阻塞代码，会阻塞整个事件循环，同一循环里的其他协程全部停摆——这就是上一节 to_thread 存在的原因。

最容易误解的一条：threading.Thread 会创建一条真正的线程；asyncio.create_task() 不创建线程，只是在事件循环中安排一个协程执行。

用三个角色打比方：

选型上：

你的任务 用什么
大量 CPU 计算 多进程，这样才能吃满多个核心
同步阻塞 I/O、不支持的异步的老 SDK 多线程
大量异步 I/O，且库支持 async / await 协程

协程这类里常见的场景：调用大模型 API、HTTP 请求、异步数据库查询、Redis 请求、WebSocket、同时处理大量用户连接、同时调用多个 Agent 工具、FastAPI 中的异步接口。

一句话总结：进程隔离性最好但开销最大，线程共享资源但要注意线程安全，协程最轻量，适合高并发的 I/O 场景。

12. 小结

真正要记住的是四件事：

一、asyncio 的价值是重叠等待时间，不是让单个操作变快。 串行 await 三次和 gather 一次，耗时差三倍。

二、create_task 是”排上号”，await 是”等结果”。 任务不需要 await 也会跑，但异常得有出口，否则会得到 Task exception was never retrieved。

三、协程里不能有同步阻塞调用。 它卡的不是当前协程，是整个事件循环。同步 SDK 一律包 asyncio.to_thread，或者换成原生异步的库。

四、await 的位置就是切换点。 协程只在 await 处让出执行权——这既解释了为什么不用加锁，也解释了为什么一个 time.sleep 能让所有协程停摆。
