Three.js 加载大规模点云

在数字孪生、WebGIS、激光雷达、自动驾驶、测绘等场景中，点云数据很容易达到千万、上亿甚至更大的规模。

如果直接把全部点云下载到浏览器，然后一次性解析并创建一个巨大的 THREE.Points，很快就会遇到几个问题：

  • 首屏下载时间很长
  • 主线程解析卡顿
  • 浏览器内存占用过高
  • GPU 上传压力大
  • 显存快速增长
  • 帧率下降，严重时页面甚至崩溃

所以，大规模点云渲染真正要解决的问题并不是：

怎么一次把所有点都画出来？

而是：

怎么只加载、只解析、只上传、只渲染当前视角真正需要的那部分点？

Potree 2.0 就是一套非常典型的大规模点云解决方案。它的核心可以概括为：

大规模点云不能一次性全部加载，我一般会采用类似 Potree 的流式加载方案。首先在离线阶段通过八叉树对原始点云做空间划分，并生成多层 LOD。运行时从根节点开始，根据相机视锥先做节点级剔除，再根据节点包围球投影到屏幕后的像素大小决定是否继续向下细分。

对当前需要的节点，通过 Point Budget 控制单帧可见点总量，并通过优先级队列优先处理屏幕占比大、离相机近的节点。

Potree 2.0 会把节点数据集中存储在 octree.bin，每个节点记录 byteOffset 和 byteSize，浏览器通过 HTTP Range 只请求当前节点对应的那一段数据，而不是下载完整点云文件。

请求回来的 ArrayBuffer 会通过 Transferable 交给 Web Worker 解码，避免阻塞主线程。解码完成后转成 BufferAttribute 和 BufferGeometry，再通过 THREE.Points 批量上传 GPU 和渲染。

同时还需要限制每帧 GPU 上传节点数量，并通过 LRU 淘汰长时间不用的节点，控制 CPU 内存和 GPU 显存。

所以核心就是：八叉树 + LOD + 视锥剔除 + HTTP Range + Web Worker + Transferable + Point Budget + GPU 上传限流 + LRU。

大规模点云优化不是单独某一项技术。

它是一整套从磁盘到 GPU 的流式系统：

最终目的只有一个：

无论原始点云有多少点，都不要让浏览器真正同时处理所有点，而是始终只处理“当前这一帧最值得显示的那部分数据”。

这就是 Three.js 加载大规模点云的核心思路。

本文从 Three.js 的角度，把这条完整链路串起来。
